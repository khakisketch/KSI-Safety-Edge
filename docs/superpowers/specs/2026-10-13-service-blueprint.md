# KSI Safety Edge — 서비스 블루프린트 (개발·검증 중심)

- 작성: 2026-10-13 · 상태: **초안 — 개발 검증 여정(S0)만 확정. 운영 여정은 현장 사용자 검증 전 미확정.**
- 근거: `docs/superpowers/specs/2026-10-08-integrated-design.md`(제품 목표·전체 흐름),
  `docs/plans/2026-10-12-b1-operator-flow-contract.md`(조종 상태 계약),
  `docs/plans/2026-10-13-a2-reviewer-annotation.md`(A-2 의견 계약).
- 경계: 이 문서는 **여정·역할·완료 증거·실패 경로**를 정의한다. 시각 설계(레이아웃·색·타이포)는
  디자인 작업 공간(`design/rc-pilot-shell/`) 소유이며, 화면 구현은 이 문서를 기준으로 한다.
  **새 API·계약·권한을 도입하지 않는다.**

## 1. 왜 이 문서가 필요한가 (문제 정의)

현장 사용자 피드백: “`/review`는 이해할 수도, 사용할 수도 없다. 내가 뭘 해야 하는지 모르겠다.”

원인은 화면 취향이 아니라 **서비스 구분의 부재**다. 한 제품 안에 성격이 다른 세 가지 일이
있는데, 화면에서는 구분되지 않았다.

1. **개발 검증** — RC에서 Core까지 데이터가 흐르는지 확인 (현재 실제 사용자 = 개발자)
2. **현장 조종** — 임무 준비·비행·종료·동기화 (조종사)
3. **비행 검토** — 사건·공백·증거 검토와 의견 기록 (안전관리자 — 운영 인증·신원이 아직 없음)

`/review`는 1과 3을 한 화면에 섞어 놓아, 시작 이유(토큰·목록)와 완료 조건(무엇이 보이면 끝인지)이
드러나지 않았다. 이 블루프린트는 **먼저 여정을 고정하고, 그다음 화면을 그 여정에 맞춘다**는
순서를 강제한다. (GOV.UK Service Manual: 사용자는 내부 시스템 구조를 알 필요가 없어야 하며,
서비스는 처음부터 끝까지 한 가지 일을 끝내게 해야 한다 — 참고 자료 1·2.)

## 2. 서비스 지도

| # | 서비스 | 사용자 | 끝내려는 일 | 현재 상태 | 진입점 |
|---|---|---|---|---|---|
| S0 | **개발 검증 서비스** (이번 확정) | 개발자(KSI) | RC→Core→조회/의견 흐름을 한 번의 재현 가능한 시나리오로 확인 | 구현됨 — `/review` 검증 콘솔 | 로컬 `127.0.0.1:8000/review` · tailnet `:8800`(아래 §5) |
| S1 | 현장 조종 서비스 | 조종사/운영자 | 임무 준비 → 비행 → 종료 → 동기화까지 오프라인에서 수행 | Android 셸 구현(C67), 실기 미검증(A9-4) | `android-rc` 앱 |
| S2 | 비행 검토 서비스(운영) | 안전관리자/검토자 | 비행 후 사건·관측 공백·증거를 검토하고 의견 기록 | 위임 대기 — 운영 인증·신원·권한 필요 | 배포 전 보안 게이트 이후 |

## 3. S0 개발 검증 여정 — 이번에 확정한 계약

**목표 문장:** “한 번의 흐름으로, 데이터가 어디까지 도착했는지와 다음에 무엇을 할지 화면에서 안다.”

콘솔은 4단계를 순서대로 안내하고, 각 단계의 **완료는 그 흐름이 실제로 실행됐다는 사실에서만**
계산한다(버튼을 눌렀다는 이유로 완료 표시하지 않는다). 진행 상태는 브라우저 탭에만 저장되며
‘검증 초기화’로 지운다 — 서버 데이터는 건드리지 않는다.

| 단계 | 사용자의 목적 | 화면이 보여야 하는 것 | 사용자가 하는 것 | 시스템 처리(기존 API) | 완료 증거 | 실패 시 다음 |
|---|---|---|---|---|---|---|
| 01 Core 연결·목록 | “이 Core가 응답하는가” | 연결 대상 origin, 토큰 상태 | 조회 토큰 입력 → 비행 불러오기 | `GET /flights` | 비행 N건이 오류 없이 표시 | 오류 문구 + 토큰 확인/재시도 안내 |
| 02 비행 데이터 도착 | “이 비행이 서버에 얼마나 도착했는가” | 비행 목록(업로드 상태·누락 artifact) | 비행 선택 | `GET /flights/{id}` + coverage·sessions·applications·observations·events·artifacts | 상세 요약(Events·Observations·Artifacts·Coverage) 표시 | 상세 오류 표시 + 다시 시도 |
| 03 사건·증거 확인 | “사건의 근거를 확인할 수 있는가” | 사건 카드, 증거 목록 | 증거 확인 · 미리보기/다운로드 · 원문 JSON 펼치기 | `GET /events/{id}` + `/evidence` + `/objects/{id}` | 연결 증거가 표시되고 미리보기·다운로드가 동작 | 증거 조회 실패 원인 표시(부분 도착 안내 포함) |
| 04 A-2 의견 흐름 | “의견이 삭제 없이 쌓이는가” | 이력(유형·사유·supersedes) | 의견 기록 (rc 토큰 필요) / 취소 기록 | `POST /events/{id}/annotations` (기존 계약) | 이력에 추가되고 원본 유지 — 취소는 REVOKE_PREVIOUS 새 기록 | 401/403은 원인 문구(토큰 스코프) + 재시도 |

**시나리오 데이터(시드):** 정상 비행(사건·증거·이력) · 사건 0건 비행 · PARTIAL 비행(누락 artifact).
시드: `scripts/review_demo_seed.py` (데모 DB 전용, 기본 저장소와 분리).

**정직 규칙(불변):** 사건 0건 ≠ 안전 · 수신 시각은 RC 수신 UTC(근사) · 관측 공백은 공백으로 표시 ·
[SIMULATED] 숨김 금지 · 실패를 성공으로 표시하지 않는다.

## 4. S1·S2 운영 여정 — 초안 (사용자 검증 전 확정 금지)

### S1 조종 여정 (B-1 계약 기반)

| 단계 | 완료 증거 | 실패 시 다음 |
|---|---|---|
| 임무 준비(사이트·번들 동기화→적용) | 적용 이력·READY가 실제 상태와 일치 | PREPARE 실패 원인 표시, 기존 적용 유지 |
| 비행 시작 | 녹화 시작 + 증거 수신 시작 | 비행 없는 시작 표시 금지 |
| 비행 중 | 상태 레일에서 ■/▲ 항목 우선 확인 | 링크 끊김/하트비트 지연 조치 문구 |
| 비행 종료 | 세그먼트 finalize·로컬 보관 표시 | 재시작 시 녹화 재개 + 손실 구간 고지 |
| 동기화 | 미동기화 수가 줄고 서버 commit 확인 | 서버 상태 추측 금지, 수동 업로드 경로 |

- 실기 게이트(A9-4): RC Plus 2 실제 렌더·햇빛 가독성·장갑 터치. **이 환경에는 Android 렌더
  경로가 없어 시각·사용성 판정 불가.**

### S2 검토 여정 (운영용 — 아직 위임 전)

| 단계 | 완료 증거 | 선행 조건(미구현) |
|---|---|---|
| 비행 선택(현장·기간 기준) | 검토 대상 비행이 사실과 함께 표시 | 사용자 인증·조직 디렉터리 |
| 관측 범위·공백 확인 | coverage·gaps·미업로드 상태 표시 | — |
| 사건·증거 검토 | 원본/프록시 구분 표시 | 프레임↔관측 매핑 검증 |
| 의견 기록 | append-only 이력 유지 | 검토자 신원·권한 |

운영 검토를 개발 검증 콘솔과 같은 서비스로 취급하지 않는다 — **A-2 의견 계약은 지금도 유효하지만,
운영 사용자 경험은 인증·신원·알림이 준비될 때까지 이 연습 콘솔이 대신하지 않는다.**

## 5. 환경·진입점 구분 (무엇이 목업이고 무엇이 실제인가)

| 산출물 | 정체 | 검증 대상 | 접근 | 주의 |
|---|---|---|---|---|
| `design/rc-pilot-shell/field-shell.html` | **목업**(모든 값 [SIMULATED]) | 시각 체계·상태 계약 표현 | `bash scripts/design_preview_server.sh` → `:8765` · tailnet `:8765` | 실제 데이터·제어가 아님 |
| `/review` 검증 콘솔 | **실제 동작**(데모 DB 기록) | 데이터 흐름·의견 API | 로컬 `:8000` · tailnet `:8800` | dev 토큰(개발용). **tailnet 전용 — 보는 기기가 Tailscale에 연결돼 있어야 열린다** |
| `android-rc` 앱 | 실제 구현(실기 미검증) | 현장 조종 흐름 | 실기/기기 | A9-4 게이트 |

  매핑 상태 확인(런북 §tailnet 접속). 공개 노출은 보안 검토 전 금지.
- 로컬 개발자용 실행 방법·데모 초기화는 `docs/verification/dev-harness-runbook.md`.

## 6. 성공의 정의 (S0)

1. 개발자가 도움 없이 §3의 4단계를 완료하고, 각 단계에서 “다음 할 일”을 화면에서 찾는다.
2. 예외 상태(토큰 오류 · 누락 artifact · 사건 0건)가 사실과 다음 행동으로 표시된다.
3. 시드 3종(정상/사건 0/PARTIAL)이 같은 스크립트로 재현된다.
4. 이 문서의 문구 의미(정직 규칙)가 화면에서 그대로 유지된다.

## 7. 다음 단계

1. **사용자(개발자) 검증** — 실제로 4단계를 수행해 막히는 지점 기록 (이번 커밋의 목적).
2. 검토자·조종자 여정은 **현장 파일럿 전 사용자 리서치**로 확정 (지금 확정 주장 금지).
3. 실기(A9-4): RC Plus 2 렌더·햇빛·장갑 — 장치 준비 후.
4. 운영 배포 전: 인증·신원·알림·HTTPS 게이트 설계 (별도 문서).
