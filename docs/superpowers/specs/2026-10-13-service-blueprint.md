# KSI Safety Edge — 서비스 블루프린트 (개발·검증 중심)

- 작성: 2026-10-13 · 갱신: 2026-10-14 · 상태: **초안 — Core 데이터 점검 여정(S0)만 확정. RC→Core 전송 검증 및 운영 여정은 별도 범위.**
- 근거: `docs/superpowers/specs/2026-10-08-integrated-design.md`(제품 목표·전체 흐름),
  `docs/plans/2026-10-12-b1-operator-flow-contract.md`(조종 상태 계약),
  `docs/plans/2026-10-13-a2-reviewer-annotation.md`(A-2 의견 계약).
- 경계: 이 문서는 **여정·역할·완료 증거·실패 경로**를 정의한다. 시각 설계(레이아웃·색·타이포)는
  디자인 작업 공간(`design/rc-pilot-shell/`) 소유이며, 화면 구현은 이 문서를 기준으로 한다.
  **새 API·계약·권한을 도입하지 않는다.**

## 1. 왜 이 문서가 필요한가 (문제 정의)

현장 사용자 피드백: “`/review`는 이해할 수도, 사용할 수도 없다. 내가 뭘 해야 하는지 모르겠다.”

원인은 화면 취향이 아니라 **서비스 구분의 부재**다. 한 제품 안에 성격이 다른 세 가지 일이
있는데, 화면에서는 구분되지 않았다.

1. **Core 데이터 점검** — Core가 이미 반환하는 비행·관측·사건·증거 레코드를 개발자가 조회·진단
2. **현장 조종** — 임무 준비·비행·종료·동기화 (조종사)
3. **비행 검토** — 사건·공백·증거 검토와 의견 기록 (안전관리자 — 운영 인증·신원이 아직 없음)

`/review`는 개발자 진단과 운영자 의견 기록을 한 화면에 섞어 놓아, 시작 이유(토큰·목록)와 완료 조건(무엇이 보이면 끝인지)이
드러나지 않았다. 또한 기존 화면은 실제로 RC 업로드를 실행하지 않으면서 end-to-end 전송을 확인하는 것처럼 표현했다.
이 블루프린트는 **먼저 여정을 고정하고, 그다음 화면을 그 여정에 맞춘다**는
순서를 강제한다. (GOV.UK Service Manual: 사용자는 내부 시스템 구조를 알 필요가 없어야 하며,
서비스는 처음부터 끝까지 한 가지 일을 끝내게 해야 한다 — 참고 자료 1·2.)

## 2. 서비스 지도

| # | 서비스 | 사용자 | 끝내려는 일 | 현재 상태 | 진입점 |
|---|---|---|---|---|---|
| S0 | **Core 데이터 점검** (이번 확정) | 개발자(KSI) | Core가 반환하는 비행 레코드·커버리지·사건·증거를 조회하고 다음 진단을 결정 | 구현됨 — `/review` Core 데이터 점검 | 로컬 `127.0.0.1:8000/review` · tailnet `:8800`(아래 §5) |
| S1 | 현장 조종 서비스 | 조종사/운영자 | 임무 준비 → 비행 → 종료 → 동기화까지 오프라인에서 수행 | Android 셸 구현(C67), 실기 미검증(A9-4) | `android-rc` 앱 |
| S2 | 비행 검토 서비스(운영) | 안전관리자/검토자 | 비행 후 사건·관측 공백·증거를 검토하고 의견 기록 | 위임 대기 — 운영 인증·신원·권한 필요 | 배포 전 보안 게이트 이후 |

## 3. S0 Core 데이터 점검 여정 — 이번에 확정한 계약

**목표 문장:** “현재 Core가 반환하는 데이터의 상태와 그다음 확인할 근거를 안다.”

콘솔은 목록·상세·증거의 **조회 응답**과 선택된 비행의 Core-side 상태를 보여준다. “조회 확인”은
해당 Core API가 응답했다는 뜻만 가진다. 이 화면은 RC 업로드를 실행하거나 대조하지 않으므로
RC→Core 전달·현장 원본·파일 내용의 진위를 증명하지 않는다. 데이터 출처는 서버가 전용 demo DB와
object-store 쌍으로 식별한 경우에만 **DEMO FIXTURE**로 표시하고, 나머지는 **출처 미확인**이다.

| 단계 | 사용자의 목적 | 화면이 보여야 하는 것 | 사용자가 하는 것 | 시스템 처리(기존 API) | 확인 증거의 의미 | 다음 진단 |
|---|---|---|---|---|---|---|
| 01 연결·목록 조회 | “이 Core API가 응답하는가” | Core origin, 데이터 출처 표식, 목록 응답 상태 | 조회 토큰 입력 → 목록 조회 | `GET /flights` | 목록 API 응답과 반환 건수만 확인 | 401/403은 토큰·조직 범위, 연결 실패는 서버 상태 확인 |
| 02 비행 상세 조회 | “이 레코드에서 Core가 보고하는 수집 상태는 무엇인가” | upload_state, manifest 커밋/전체 수, 누락 artifact 수 | 비행 선택 | flight·coverage·sessions·applications·observations·events·artifacts GET | Core 응답값을 확인. RC 업로드가 성공했다는 증거는 아님 | PARTIAL/누락 수를 manifest·artifact 응답과 대조 |
| 03 관측·사건 확인 | “Core가 어떤 레코드를 반환하는가” | coverage, gaps, 관측 표본, 사건 건수 | 커버리지·관측·사건 확인 | 기존 GET API | 반환된 레코드와 누락은 구별됨. 사건 0건 ≠ 안전 | 응답 0건은 로컬 상태를 단정하지 않고 source/조직 범위 확인 |
| 04 증거 응답 확인 | “사건 참조와 Core artifact 응답이 맞는가” | event 참조 ID와 evidence API 반환 건수 | 증거 조회, 필요 시 미리보기/다운로드 | `GET /events/{id}` + `/evidence` + `/objects/{id}` | evidence API 응답만 확인. 다운로드·육안 확인 전에는 파일 내용/출처를 검증하지 않음 | 0건·부분 응답이면 event ID와 manifest artifact를 대조 |

**시나리오 데이터(시드):** 정상 비행(사건·증거·이력) · 사건 0건 비행 · PARTIAL 비행(누락 artifact).
시드: `scripts/review_demo_seed.py` (데모 DB 전용, 기본 저장소와 분리).

**분리된 개발 기능:** A-2 이력 조회/기록/취소는 고급 개발용 write-path 테스트다. 기록·취소는 현재 연결된 Core에 실제 append-only 레코드를 추가하지만 운영자의 안전 검토 경험이나 실제 검토 행위를 뜻하지 않는다. 실제 운영 검토 서비스는 §4 S2와 별개다.

**정직 규칙(불변):** 사건 0건 ≠ 안전 · 수신 시각은 RC 수신 UTC(근사) · 관측 공백은 공백으로 표시 ·
[SIMULATED] 숨김 금지 · 실패를 성공으로 표시하지 않는다.

## 4. S1·S2 운영 여정 — 초안 (사용자 검증 전 확정 금지)

### S1 조종 여정 (B-1 계약 기반)

| 단계 | 완료 증거 | 실패 시 다음 |
|---|---|---|
| 임무 준비(사이트·번들 동기화→적용) | 적용 이력·READY가 실제 상태와 일치 | PREPARE 실패 원인 표시, 기존 적용 유지 |
| 비행 시작 | 녹화 시작 + 증거 수신 시작 | 비행 없는 시작 표시 금지 |
| 비행 중 | 상태 레일에서 ■/▲ 항목 우선 확인 | 링크 끊김/하트비트 지연 조치 문구 |
| 비행 종료 | 세그먼트 finalize·로컬 보관 표시 | 재시작 시 녹화 재개 + 손실 구간 고지 |
| 동기화 | 미동기화 수가 줄고 서버 commit 확인 | 서버 상태 추측 금지, 수동 업로드 경로 |

- 실기 게이트(A9-4): RC Plus 2 실제 렌더·햇빛 가독성·장갑 터치. **이 환경에는 Android 렌더
  경로가 없어 시각·사용성 판정 불가.**

### S2 검토 여정 (운영용 — 아직 위임 전)

| 단계 | 완료 증거 | 선행 조건(미구현) |
|---|---|---|
| 비행 선택(현장·기간 기준) | 검토 대상 비행이 사실과 함께 표시 | 사용자 인증·조직 디렉터리 |
| 관측 범위·공백 확인 | coverage·gaps·미업로드 상태 표시 | — |
| 사건·증거 검토 | 원본/프록시 구분 표시 | 프레임↔관측 매핑 검증 |
| 의견 기록 | append-only 이력 유지 | 검토자 신원·권한 |

운영 검토를 Core 데이터 점검 도구와 같은 서비스로 취급하지 않는다 — **A-2 의견 계약은 지금도 유효하지만,
운영 사용자 경험은 인증·신원·알림이 준비될 때까지 이 연습 콘솔이 대신하지 않는다.**

## 6. 성공의 정의 (S0)

1. 개발자가 연결·출처 표식·선택 비행 상태를 구분하고, Core 응답에 근거한 다음 진단을 찾는다.
2. 토큰 오류·누락 artifact·사건 0건·증거 0건이 사실대로 표시되며 업로드 성공이나 안전 판정을 추론하지 않는다.
3. 시드 3종(정상/사건 0/PARTIAL)은 동일 스크립트로 재현되고 DEMO FIXTURE로 식별된다.
4. RC→Core end-to-end 검증은 별도 RC 실행/expected-record 대조 절차가 생기기 전까지 완료로 주장하지 않는다.

## 7. 다음 단계

1. **개발자 Core 점검 검증** — 출처 표식·상태 요약·다음 조치가 혼동 없이 읽히는지 확인.
2. RC→Core end-to-end 검증이 필요하면 실제 RC 기록과 Core 수신 근거를 상관시키는 별도 테스트를 설계한다.
3. 검토자·조종자 여정은 **현장 파일럿 전 사용자 리서치**로 확정 (지금 확정 주장 금지).
4. 실기(A9-4): RC Plus 2 렌더·햇빛·장갑 — 장치 준비 후.
5. 운영 배포 전: 인증·신원·알림·HTTPS 게이트 설계 (별도 문서).
