# RC UI — 전체 화면 판단과 증거

이 문서는 **검토 방법**이다. 새로운 화면 계약·디자인 승인·장비 접근 권한을 만들지 않는다.
제품 의미는 `AGENTS.md`의 정본, 현행 시각 체계는 `DESIGN.md`, 실행 경로는 개발 하네스 런북을 따른다.
프로젝트는 전역 역할·모델·스킬·위임 정책을 재정의하지 않는다.

## 바뀌지 않는 의미와 바꿀 수 있는 표현

- 불변: 실제 근거/미확인/지연의 구별, 명령 게이트, AI/카메라/KSI/보존 주체의 구별, 실제 자료 보존.
- 사용자 방향:4탭·영상 중심 비행 골격·물리 RC와의 역할 분담. 제약을 삭제해 간결하게 만들지 않는다.
- 현재 구현의 위치·칩 폭·지도 크기·폼/팝업·계기의 균등 분산은 설계 가설이다.
  이전 라운드의 숫자와 검사 통과를 영구 승인으로 승격하지 않는다.48dp는 조작 영역 기준이지 읽기 띠의 높이가 아니다.

## 설계 전에 먼저 판단할 것

1. 제품 여정에서 지금 사용자가 결정/수행할 일과 다음 화면을 짚는다. 연결 전 상태만 제품 전체로 보지 않는다.
2. 최신 전체 화면과 실제 연결 파일을 확인한다. 사용자 지적 외에도 시선 순서·정보 밀도·조작 식별·장면 점유를 판단한다.
3. 비일상적 변경에는 필요한 실제 레퍼런스의 **구성 원리**를 관찰한다. 링크/조사 횟수는 산출물이 아니다.
   `관찰한 원리 → 제품에서 내린 결정 → 포기한 대안/이유 → 전체 화면에서 볼 근거`를 짧게 남긴다.
   같은 실패 검색을 반복하지 않고 모르는 것은 모르는 상태로 둔다. 자산/라이선스·외부 전송 정책을 지킨다.
4. 선택은 Design이 추천한다. 계약·안전·비용·큰 사용자 선택이 아니면 사용자를 반복적인 디자인 디렉터로 만들지 않는다.
   전면 재설계 요청을 기존 버튼의 간격 조절로 축소하지 않으며, 좁은 수정 요청을 임의 전면 교체로 키우지도 않는다.

## 같은 전체 화면에서 검토할 질문

- 영상이 주 작업면으로 읽히는가? AI·렌즈·지도 부재·복구·계기가 동등한 큰 블록으로 경쟁하지 않는가?
- 자주 읽는 값, 현재 상태, 조작할 수 있는 부분이 구별되는가? 눌러야 알 수 있는 상태를 상시 장문으로 만들지 않았는가?
- 그룹 안은 가깝고 그룹 사이는 분명한가? 글자 기준선·아이콘·숫자 시작선이 맞는가?
- 지도/상세/카메라 보조를 열어도 비행 사실·복구가 남는가? 일반 설정 폼을 운용 HUD에 그대로 옮기지 않았는가?
- 예외/실패 때 무엇이 바뀌고 어떤 행동으로 돌아오는가? 조작 응답과 실제 기체 결과를 구별했는가?

검사 항목마다 체크했다는 선언 대신, 읽은 전체 캡처와 관찰/미검증을 남긴다.
참고 원리와 결과가 맞지 않으면 요소의 존재만으로 채택 성공을 주장하지 않는다.

## 상태·장면·시간은 다른 증거다

- 상태: 연결 전/입력 없음, 정상 입력, 관측·저장 장애, 요청 응답 대기·미확인과 복구를 구별한다.
- 장면: 가독성 시험은 별도 bench/검토 환경의 대표 장면으로 할 수 있다. 입력 출처·용도와
  실제 영상이 아닌 한계는 작업 보고서/캡처 메타데이터에 남긴다. 독립 디자인 시안에는 시안임을
  알리는 배지를 두지 않으며, 연결된 앱에서 모의 입력이 실제 보고와 섞일 수 있을 때는 출처를 표시한다.
  밝은 하늘/복잡한 지면/명암 변화 등 실제 사용 조건을 고르되, 운용 앱에 자료를 심거나 실제
  카메라·AI 연결 증거와 섞지 않는다. 회색 빈 화면만으로 영상 위 가독성을 판정하지 않는다.
- 시간: 정지된 REC 시간/촬영 확인 라벨은 표시 모델의 예다. 시간 증가·촬영 순간·실패·지연·재진입·복귀는
  별도 모의 전이 또는 승인된 실제 입력으로 확인한다. 촬영 버튼을 눌렀다는 사실을 저장 성공으로 만들지 않는다.
- 연결: `미연결 어댑터`, `배선됐지만 미검증`, `모의 입력`, `실제 입력 관찰`을 구별한다.
  기술 담당 실행 실패로 빠진 배선을 UX 담당의 정지 예시로 대신 완료 처리하지 않는다.

## 검토와 종료

실제 대상에 적용하고 해당 스킬의 제한된 배치 검토를 따른다. 빌드/게이트/자료 보존 검사와
전체 화면/과업/시간 전이 판단은 분리한다. 회귀 검사 통과는 디자인의 전문성 점수가 아니다.
Critic에는 원래 목표·수정 전후 전체 화면·실제 상태 범위와 반증 질문을 준다.
`이 버튼/폭이 바뀌었는가`만 묻는 수정 확인으로 전체 화면 검토를 대신하지 않는다.

수정 후에도 중요한 구성/행동 문제가 남으면 완료 표현을 낮추는 대신 문제를 해결하거나,
제한된 검토 범위의 **부분 결과와 남은 문제**를 명확히 남긴다. 무한 폴리싱이나 인수 기준 약화로 통과시키지 않는다.
최종 보고는 적용 범위·실제 증거·기능 연결의 갭·사용자 인수 여부를 구별한다.
